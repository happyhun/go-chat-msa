## 1. 아키텍처 개요

### 1.1 설계 목표와 범위

Go Chat MSA의 목표는 **높은 부하에서도 낮은 메시지 전달 지연을 유지하고, 여러 인스턴스로 확장되는 환경에서도 메시지 정합성을 지키는 것**입니다. 연결과 메시지가 늘어날 때 처리량만 높이는 데 그치지 않고, 전달 지연과 메시지의 중복·누락·순서를 함께 다룹니다.

두 목표를 함께 달성하려면 송신 과정에서 어디까지 완료를 기다릴지 정해야 합니다. 저장과 모든 수신 확인을 기다리면 지연이 커지고, 확인 없이 전달만 하면 장애 후 메시지를 추적하고 복구하기 어렵습니다. 따라서 JetStream에 기록한 뒤 메시지를 수락하고, MongoDB 저장과 수신자별 복구는 비동기로 처리합니다. 브로커에 기록하는 시간은 감수하되, DB 저장과 모든 수신자의 처리가 끝날 때까지 기다리지는 않는 절충입니다.

저지연을 위해 부하가 늘어도 실시간 전달 과정의 대기를 제한합니다. 정합성을 위해 재전달·재시도에 따른 중복 저장을 막고, 실시간으로 받지 못한 메시지는 저장된 이력으로 보충합니다. 수락·수신·저장은 서로 다른 시점에 완료되며, 모든 수신자의 동시 반영이나 전체 메시지의 인과 순서를 보장하지는 않습니다.

부하가 걸린 상태에서 전달 지연과 오류·거절을 함께 측정해 이 절충이 효과적인지 확인합니다. 스케일아웃·재연결·저장 장애에서는 수신이 확인된 메시지 집합과 최종 DB 상태를 대조합니다. 실행 기준은 로컬 kind의 `dev`/`test`/`qa`입니다. 저장소가 `emptyDir`을 사용하므로 데이터 복구는 저장소 Pod와 데이터가 유지되는 동안에만 가능합니다.

### 1.2 서비스 책임

연결 관리, 인증, 메시지 저장은 부하 특성이 다릅니다. 각 작업을 별도 서비스가 맡아 독립적으로 자원을 배분하고, DB 저장이 늦어져도 실시간 송수신이 직접 기다리지 않도록 합니다.

| 서비스 | 책임 | 통신 | 상태/저장소 |
| :--- | :--- | :--- | :--- |
| api-gateway | REST API, JWT 검증, WebSocket 티켓 발급 | HTTP, gRPC, 내부 HTTP | Redis (티켓, 요청 제한) |
| websocket-service | 연결 검증, 로컬 세션과 Hub, 메시지 발행·구독 | WebSocket, NATS, user gRPC, 내부 HTTP | 로컬 세션, Redis (티켓 소비, 연결 제한) |
| user-service | 사용자·방·멤버십, 리프레시 토큰 | gRPC | PostgreSQL, Redis |
| chat-service | 메시지 소비·배치 저장, 이력·복구 조회 | NATS JetStream, gRPC | MongoDB |

각 WebSocket Pod는 로컬 세션이 있는 방을 NATS로 구독합니다. 사용자 채팅은 JetStream에 먼저 기록한 뒤 Core NATS RePublish로 전달하며, chat-service가 별도로 소비해 MongoDB에 저장합니다. 이력 조회와 누락 복구는 MongoDB를 사용합니다.

### 1.3 서비스 간 통신

브라우저는 같은 호스트의 `/api`와 `/ws`를 사용합니다. Traefik이 Gateway API의 `HTTPRoute`에 따라 REST는 api-gateway로, WebSocket은 websocket-service로 전달합니다.

| 경로 | 방식 |
| :--- | :--- |
| api-gateway → user/chat-service | gRPC 조회·도메인 요청 |
| websocket-service → user-service | gRPC 멤버십 확인 |
| api-gateway → websocket-service | 내부 HTTP 시스템 메시지·방 세션 종료 |
| websocket-service → JetStream | 사용자 채팅 발행 후 응답 대기 |
| NATS → websocket-service | Core 방 메시지·제어 이벤트 구독 |
| chat-service → JetStream | 공유 durable pull consumer에서 메시지 수신 |

### 1.4 핵심 기술 선택

| 영역 | 선택 | 설계상 역할 |
| :--- | :--- | :--- |
| 런타임 | Go 1.27 | 연결별 송수신과 비동기 작업 처리, 정적 바이너리 배포 |
| API 계약 | `net/http`, OpenAPI, gRPC, Buf | 외부 REST와 내부 서비스 계약을 명시하고 생성 코드로 호출부 일치 확인 |
| 메시징 | WebSocket, NATS Core + JetStream | 장기 연결, Pod 간 fan-out, 저장 대기 메시지 보관 |
| 도메인 데이터 | PostgreSQL, MongoDB | 관계·트랜잭션과 메시지 저장·조회 부하 분리 |
| 제어 상태 | Redis | 인증 상태, 일회성 티켓, 공유 처리율 제한 |
| 실행·검증 | Kubernetes, Kustomize, Testcontainers | 환경별 배포와 실제 의존성을 사용하는 검증 |
| 관측성 | OpenTelemetry, Grafana Stack | 로그·메트릭·트레이스·프로파일 연계 |

## 2. 도메인과 핵심 동작 흐름

저지연과 정합성을 함께 판단하려면 메시지를 수락한 시점과 수신·조회할 수 있는 시점을 구분해야 합니다. 데이터 소유권, 연결, 전송, 복구 순서로 각 단계의 완료 조건과 실패 시 동작을 설명합니다.

### 2.1 데이터 소유권과 멤버십

| 데이터 | 소유 서비스 | 저장소와 모델 |
| :--- | :--- | :--- |
| 사용자·채팅방·멤버십 | user-service | PostgreSQL `users`, `rooms`, `room_members` |
| 사용자 채팅 이력 | chat-service | MongoDB `messages` |
| 저장 대기 메시지 | websocket-service 발행, chat-service 소비 | NATS JetStream 스트림과 durable consumer |
| 리프레시 토큰 | user-service | Redis의 유효·사용 완료 토큰 상태와 사용자별 토큰 목록 |
| 연결 티켓·HTTP 제한 | api-gateway, websocket-service | Redis의 TTL 기반 제어 상태 |

`room_members`는 사용자와 방의 복합 키로 멤버십을 관리합니다. 방 참여·나가기는 멤버십을 변경하는 REST 동작이며, WebSocket 접속·종료는 연결 상태만 바꿉니다. 같은 사용자가 여러 탭에서 같은 방에 접속할 수 있습니다.

사용자·방·메시지 ID는 UUIDv7입니다. 메시지는 작성자 ID, 클라이언트 메시지 ID, 방 ID, 종류, 본문, 생성 시각을 저장합니다. 참여·나가기 시스템 알림은 실시간으로만 전달하며 채팅 이력에 저장하지 않습니다.

### 2.2 인증과 WebSocket 연결

#### 로그인과 토큰 갱신

user-service는 로그인에 성공하면 유효 기간이 짧은 HS256 액세스 토큰과 사용자 정보를 담지 않는 UUID 기반 리프레시 토큰을 발급합니다. api-gateway는 `Authorization: Bearer`로 전달된 액세스 토큰의 서명, 사용자 정보, 만료 시간을 검증합니다. 발급·검증 서비스가 시크릿을 공유하므로 공개키 배포 없이 검증할 수 있으며, 액세스 토큰의 유효 기간 중 별도 폐기 상태는 두지 않습니다.

리프레시 토큰은 원문 대신 SHA-256 해시로 Redis에 등록합니다. TTL로 만료를 관리하고, 갱신할 때마다 Lua 스크립트로 기존 토큰의 폐기, 사용 완료 표시, 새 토큰 등록을 하나의 원자적 연산으로 처리합니다. 이미 사용한 토큰이 다시 들어오면 재사용으로 판단해 해당 사용자의 유효 리프레시 토큰을 모두 폐기합니다.

로그아웃은 요청에 사용한 리프레시 토큰을 폐기합니다. Redis 장애로 인증 상태를 확인하거나 갱신할 수 없으면 로그인·갱신·로그아웃은 실패합니다.

브라우저의 리프레시 토큰은 `HttpOnly`, `SameSite=Strict` 쿠키로 전달합니다. 프론트엔드와 API는 동일 출처로 접근하며, `ENV=prod`이면 `Secure` 속성이 켜집니다. dev/test/qa는 로컬 HTTP를 사용합니다.

#### 일회성 티켓과 연결 준비

브라우저 WebSocket API는 `Authorization` 헤더를 직접 지정할 수 없습니다. 연결 URL에 수명이 긴 JWT를 넣는 대신, 인증된 REST 요청으로 30초 TTL의 일회성 티켓을 받습니다.

1. 클라이언트가 `POST /api/auth/ws-ticket`으로 티켓을 발급받습니다.
2. `GET /ws?room_id=...&ticket=...` 요청을 받은 websocket-service가 연결 처리율 제한을 검사하고 Redis `GETDEL`로 티켓을 소비합니다.
3. user-service를 통해 방 멤버십을 확인합니다.
4. 해당 방의 로컬 Hub를 준비합니다. 새 Hub이면 Core NATS가 구독 요청을 처리했는지 flush로 확인합니다.
5. 준비가 끝나면 WebSocket으로 연결을 전환하고 세션을 등록합니다. 준비 단계에서 실패하면 HTTP 오류를 반환합니다. 연결 전환이나 세션 등록에 실패하면 준비 상태를 정리하고, 이미 전환된 연결은 닫습니다.

연결 과정에서 소비한 티켓은 연결에 실패해도 다시 사용할 수 없으므로 재시도에는 새 티켓이 필요합니다. 마지막 로컬 세션이 나간 Hub는 기본 5분 동안 새 세션이 없으면 구독을 해제합니다.

### 2.3 메시지 수락·전달·저장

1. 클라이언트가 `client_msg_id`, `content`를 담은 채팅 프레임을 보냅니다.
2. websocket-service가 사용자·방 단위 처리율 제한과 메시지 형식을 검사하고 UUIDv7 서버 ID를 생성합니다.
3. `chat.persist.{roomID}`로 메시지를 발행하고 JetStream의 응답을 기다립니다. `PubAck`가 성공하면 수락된 것으로 판단합니다.
4. JetStream은 기록한 메시지를 Core RePublish를 통해 `room.msg.{roomID}`로 재발행합니다. 같은 방을 구독한 각 Pod가 로컬 세션에 전달하며, 발신자도 자신이 보낸 메시지를 같은 경로로 돌려받습니다(echo).
5. chat-service가 durable consumer에서 메시지를 가져와 MongoDB에 배치 저장하고, 저장 결과에 따라 ACK·재시도·DLQ를 처리합니다.

수락, 실시간 수신, MongoDB 저장은 서로 다른 시점에 완료됩니다. WebSocket에 데이터를 썼다는 사실만으로 JetStream에 기록되었다고 볼 수는 없습니다. RePublish를 통해 받은 echo는 스트림 기록을 확인해 주지만, MongoDB 저장 완료나 발신 Pod의 `PubAck` 수신까지 증명하지는 않습니다.

클라이언트에 수락을 알리는 별도의 ACK 프레임은 없습니다. 발행에 실패하면 성공을 알리는 echo를 직접 만들지 않고 송신 세션을 닫습니다.

Core NATS로 각 Pod에 메시지를 전달할 때는 Pod별 ACK나 재생 기능을 사용하지 않습니다. 전송 큐가 가득 차 프레임이 버려지면 이후 수신한 `frame_no`의 번호가 건너뛰는 것으로 누락 가능성을 감지하고, 이력 조회로 복구를 시도합니다.

### 2.4 이력 조회와 재연결 복구

`GET /rooms/{id}/messages`는 user-service에서 방 멤버십과 가입 시각을 확인한 뒤 chat-service에 이력을 조회합니다.

| 쿼리 | 동작 |
| :--- | :--- |
| `after_id` 없음 | 가입 시각 이후의 최근 이력, ID 내림차순 |
| `after_id` 있음 | 해당 ID 이후를 오름차순 반환; 빈 값이면 가입 시각 이후부터 조회 |
| `limit` | 기본 이력 100개·동기화 50개, 최대 1000개; `has_more`로 다음 페이지 판단 |

클라이언트는 서버 ID와 `(room_id, sender_id, client_msg_id)`로 중복을 제거하고 UUIDv7 ID로 정렬합니다. 서버 echo는 같은 클라이언트 키의 임시 메시지를 교체합니다. 실시간 도착 순서와 DB 저장 순서는 이 정렬 순서와 다를 수 있습니다.

늦게 저장된 메시지도 찾을 수 있도록 조회 시작점을 이전 시각으로 되돌립니다. 복구 중에는 이 시작점을 고정하고, 조회할 때마다 그 지점부터 페이지를 다시 읽습니다. 실시간 메시지를 받거나 조회 결과가 비어 있어도 시작점을 앞으로 옮기지 않습니다. 사용자·방별 시작점은 `sessionStorage`에 보관합니다. 재연결하거나 화면에 다시 포커스가 왔을 때, 또는 수동으로 복구할 때 이 시작점을 재사용합니다.

| 동작 | 범위 |
| :--- | :--- |
| 재연결 | 무작위 지연을 섞은 백오프, 연속 실패 최대 20회; 안정적으로 유지된 연결 종료 시 횟수 초기화 |
| 재연결 중단 | 티켓 발급의 401·403·429 응답 |
| 복구 계기 | 재연결, `frame_no` 간격, 화면 포커스 복귀, 수동 복구 |
| 반복 복구 | 커서 기준 시각을 2초 이전으로 이동, 최대 60초간 무작위 지연을 섞은 백오프 |
| 조회 제한 | 요청당 5초, 모든 페이지를 읽는 시간은 남은 복구 시간 이내 |
| 주기적 보충 | 30초마다 최근 커서를 이전 시각으로 되돌려 조회, 전체 조회 제한 시간 5초 |
| 송신 결과 미확인 | echo가 10초 안에 오지 않으면 표시, 자동 재전송 없음 |

반복 기간이 끝나고 마지막 조회 오류가 남으면 재동기화 안내를 표시합니다. 성공 응답에 특정 메시지가 없다는 사실만으로 누락을 판정하지 않습니다. 재전송에는 기존 `client_msg_id`를 사용합니다.

이 복구 방식은 정해진 기간 동안 반복 조회해 늦게 저장된 메시지를 보충합니다. 메시지에 연속 순번이 없으므로 모든 누락을 찾아냈거나 복구를 마쳤다고 증명할 수는 없습니다. 조회 시작점을 되돌리는 범위와 재시도 기간을 넘어서는 지연·시계 차이까지 보장하지는 않습니다.

작성자 이름은 메시지에 저장하지 않습니다. 클라이언트는 방 멤버 목록으로 캐시를 만들고, 처음 보는 작성자 ID를 `GET /users?ids=...`로 일괄 조회합니다. 탈퇴로 사용자 행이 없으면 `(탈퇴한 사용자)`로 표시하며, 이름 조회 실패가 메시지 이력 조회를 막지는 않습니다.

### 2.5 방·회원·세션 종료

| 동작 | 도메인 변경 | 실시간 알림 |
| :--- | :--- | :--- |
| 방 참여 | 멤버십 등록 | 참여 시스템 메시지 |
| 방 나가기 | 멤버십 삭제, 필요 시 방장 위임·빈 방 삭제 | 나가기 시스템 메시지 |
| 방 삭제 | 방 삭제 | `room_closed` 제어 이벤트로 세션 종료 |
| 화면 이탈·연결 종료 | 멤버십 유지 | 없음 |

참여·나가기 알림과 방 종료는 api-gateway가 내부 HTTP로 websocket-service에 요청하고, 요청받은 Pod가 Core NATS로 전파합니다. DB 변경 뒤 내부 HTTP 요청이 실패하면 로그를 남기며 재시도하지 않습니다. 제어 이벤트에도 Pod별 ACK·재전달이 없어 일부 기존 세션이 남을 수 있습니다. NATS 단절 시 세션을 닫는 처리만으로 이 실패를 복구할 수는 없습니다.

회원탈퇴 시에는 비밀번호를 재검증하고 모든 리프레시 토큰을 폐기한 뒤, 가입한 방을 정리하고 사용자 행을 삭제합니다. 방 정리와 사용자 삭제는 하나의 PostgreSQL 트랜잭션으로 처리합니다. 탈퇴한 사용자가 방장이면 다른 멤버에게 위임하고, 혼자 남은 방은 삭제합니다.

탈퇴 후 사용자 행을 보관할 필요가 없어 물리 삭제를 사용합니다. 같은 사용자 이름은 다시 사용할 수 있으며, 탈퇴 유예 기간과 계정 복구는 제공하지 않습니다.

### 2.6 API 계약과 접근 제어

외부 REST는 [OpenAPI 명세](../api/openapi/openapi.yaml), 내부 gRPC는 [proto 계약](../api/proto/)으로 정의합니다. REST는 리소스 중심 경로와 `snake_case` 필드, Problem Details 오류 응답을 사용합니다. gRPC는 동작 중심 메서드와 상태 코드로 결과를 표현하며, 생성 코드로 호출부의 타입을 맞춥니다.

Gateway는 JSON·필수 필드·페이지 범위처럼 요청 해석에 필요한 검증을 하고, 도메인 서비스가 비밀번호 정책·방 정원·권한 등의 최종 규칙을 검증합니다. 내부 HTTP는 `X-Internal-Secret`을 검증하며, 시스템 메시지 발행과 방 세션 종료에 사용합니다.

| 제한 대상 | 기준 | 기본값 | 상태 위치 |
| :--- | :--- | :--- | :--- |
| 공개 REST | IP | 초당 5회 / 순간 10회 | Redis |
| 인증 REST | 사용자 ID | 초당 10회 / 순간 20회 | Redis |
| WebSocket 티켓 | 사용자 ID | 초당 2회 / 순간 5회 | Redis |
| WebSocket 연결 | IP | 초당 5회 / 순간 10회 | Redis |
| 채팅 전송 | 사용자 ID + 방 ID | 초당 2회 / 순간 5회 | Pod 메모리 |

HTTP 제한 초과는 429와 `Retry-After`로 알리고, 채팅 전송 제한은 연결을 유지한 채 세션에 경고를 보냅니다. 내부 HTTP 경로는 제한 대상에서 제외합니다.

HTTP 제한은 여러 Pod가 상태를 공유해야 하므로 Redis를 사용하며, 제한기 장애 시에는 경고를 남기고 요청을 통과시킵니다. 인증·티켓의 유효 상태 확인과는 별도의 실패 정책입니다. 채팅 전송 제한은 메시지마다 Redis를 호출하는 비용을 피하기 위해 Pod 메모리에서 검사하므로 전역 제한은 아닙니다.

IP 제한은 `X-Forwarded-For`의 첫 값을 사용합니다. 앱 자체가 신뢰할 프록시 대역을 판별하는 구조는 아니므로 외부 운영 환경에서는 프록시 신뢰 경계를 보강해야 합니다.

## 3. 주요 의사결정

주요 의사결정은 송신 과정에서 무엇을 기다리고, 무엇을 재전달·복구에 맡길지에 관한 것입니다. 연결을 분산해 처리 여력을 늘리고, 수락 기준을 명확히 정해 메시지를 추적하며, 멱등 저장으로 중복 처리를 막습니다. 큐·배치·재시도는 일시적인 부하와 장애를 흡수하지만, 용량을 넘으면 요청을 거절하거나 복구가 늦어지는 비용이 따릅니다.

### 3.1 방별 담당 Pod 없는 연결 분산

같은 방의 연결을 특정 Pod에 모으면 해당 방의 부하를 여러 Pod가 나눠 처리하기 어렵습니다. 어느 Pod에 연결되었든 같은 방의 메시지를 받을 수 있도록 새 연결을 여러 Pod에 분산합니다. 각 Pod가 로컬 세션을 가진 방을 일반 Core NATS subscription으로 구독하면 방 소유권이나 sticky session 없이 모든 참여 Pod에 메시지를 전달할 수 있습니다. queue subscription은 한 Pod에만 전달하므로 방 fan-out에는 맞지 않습니다.

Pod 증설은 새 연결의 수용 능력을 늘리지만 기존 연결을 이동시키지는 않습니다. 축소·재시작으로 끊어진 연결은 클라이언트가 새 티켓으로 다시 연결하고 이력을 보충합니다. 따라서 이 구조는 연결 분산을 단순하게 하는 대신 재연결과 누락 복구를 클라이언트 프로토콜의 일부로 다룹니다.

새 Hub는 구독 요청의 처리를 flush로 확인한 뒤 세션을 받습니다. 연결 준비 단계에서 NATS 응답을 기다리는 비용을 들여, 메시지를 받을 준비가 된 뒤에만 연결을 수락합니다. 연결 이후 Core fan-out은 Pod별 수신 확인을 기다리지 않으므로, 전달 누락은 이력 조회로 보충해야 합니다.

### 3.2 메시지 수락과 조회의 장애 경계 분리

MongoDB가 잠시 응답하지 않는다는 이유로 메시지 수락까지 중단하면 JetStream의 저장 대기 기능을 활용할 수 없습니다. chat-service는 NATS 연결 상태와 MongoDB 조회 가능 상태를 별도의 상태 검사 결과로 제공하고, Kubernetes readiness는 수락 경로를 기준으로 삼습니다.

이 선택으로 MongoDB 장애 중에도 JetStream 용량 내에서는 채팅을 수락할 수 있지만, 이력 조회와 복구는 실패하거나 늦어질 수 있습니다. 반대로 NATS 단절이나 과도한 전달 지연은 세션을 종료해 재연결·복구를 유도합니다. 저장이 늦어지면 메시지를 대기열에 남기고, 전달 경로에 문제가 생기면 연결을 끊고 다시 복구하도록 하는 선택입니다. readiness는 스트림 여유 공간이나 다음 발행 성공까지 보증하지 않습니다.

| 상황 | 처리 |
| :--- | :--- |
| NATS 연결 단절 | readiness를 내리고 시차를 두고 기존 세션 종료, NATS 재연결과 세션 정리 후 새 연결 허용 |
| 방 구독 slow consumer 또는 전달 지연 한도 초과 | 해당 방의 로컬 세션 종료 후 재연결·동기화 |
| 세션 전송 큐 포화 | 해당 프레임 폐기, `frame_no`와 주기적 동기화로 복구 시도 |
| MongoDB 장애 | 조회 실패, 저장 워커의 메시지 수신 중단·DB 상태 점검, JetStream 용량 내 새 채팅 수락 |
| JetStream 용량 초과·발행 실패 | 새 채팅 수락 실패, 송신 세션 종료 |
| Pod 종료·축소 | 로컬 세션 종료·구독 해제, ACK하지 않은 저장 작업 재전달 |

#### 서비스별 준비 상태

| 서비스 | 준비 상태 검사 |
| :--- | :--- |
| api-gateway `/ready` | Redis `PING`, user-service의 gRPC 상태, `chat.v1.ChatCommand` health |
| websocket-service `/ready` | Redis `PING`, user-service의 gRPC 상태, Manager 동작, NATS 연결 |
| user-service gRPC health | PostgreSQL 상태 |
| chat-service `chat.v1.ChatCommand` | NATS 연결 상태, Kubernetes readiness가 사용 |
| chat-service `chat.v1.ChatQuery` | MongoDB 상태 점검 결과 |

`ChatCommand`와 `ChatQuery`는 gRPC 상태 검사에 사용하는 서비스 이름입니다. 별도 송신 RPC는 없으며 채팅은 WebSocket에서 JetStream으로 발행합니다. 조회 장애와 수락 가능 상태를 분리하므로 클라이언트는 실시간 연결 성공과 이력 조회 성공을 별도로 처리해야 합니다.

### 3.3 액터 모델과 상태 소유권

WebSocket Service는 Router, Manager, Hub, Session의 네 계층으로 구성됩니다. 각 계층이 연결 준비, 방 생명주기, 로컬 브로드캐스트, 개별 송수신을 맡아 상태 변경 범위를 분리합니다. 의존 방향은 상위 계층에서 하위 계층으로 흐릅니다.

```
Router (1)
└── Manager (1)
    ├── Hub (채팅방 A)
    │   ├── Session (유저 1)
    │   └── Session (유저 2)
    └── Hub (채팅방 B)
        └── Session (유저 3)
```

세션 등록·종료와 메시지 전달이 동시에 발생하므로, 공유 상태를 여러 고루틴에서 직접 변경하면 잠금 범위와 변경 순서를 추적하기 어렵습니다. Manager와 Hub는 액터 모델로 각 상태의 변경을 직렬화합니다. Manager는 Hub 목록과 생명주기를 단일 `select` 루프에서 관리하고, Hub는 세션 목록과 브로드캐스트를 자기 루프에서 순서대로 처리합니다. 외부와는 채널 또는 주입된 함수로만 통신해 공유 상태를 직접 잠그는 범위를 줄입니다. Hub가 종료에 들어가면 원자적 플래그와 종료 채널로 새 세션 등록과 메시지 전달을 거절합니다.

직렬화로 로컬 상태의 변경 순서는 명확해지지만, 이벤트 루프의 처리 용량에는 한계가 있습니다. 채널 포화와 느린 소비자는 별도의 과부하 정책으로 처리합니다. 또한 로컬 상태를 순서대로 처리한다고 해서 Pod 사이의 메시지 순서까지 보장되지는 않습니다.

#### 계층별 책임

| 계층 | 책임 |
| :--- | :--- |
| Router | HTTP 요청을 검증하고 WebSocket 연결 전환 전까지의 준비 절차를 조율 |
| Manager | Hub·구독의 생성과 종료, NATS 발행·이벤트 처리를 관리 |
| Hub | 한 방의 로컬 세션과 브로드캐스트를 직렬 처리 |
| Session | 개별 WebSocket 연결의 읽기/쓰기와 메시지 검증을 담당 |

#### 부모 직접 참조 차단

자식 계층이 부모를 직접 참조하면 순환 의존이 생깁니다. 상향 통신이 필요한 경우에도 자식이 부모의 구체 타입을 모르도록 제한합니다.

상향 통신에는 송신 전용 채널과 콜백 함수를 사용합니다. 부모의 작업 큐에 넘기는 일은 채널로 전달하고, 즉시 결과가 필요한 일은 콜백으로 호출합니다.

| 방식 | 쓰는 기준 | 이 프로젝트의 예 |
| :--- | :--- | :--- |
| 송신 전용 채널 | 자식이 부모의 작업 큐나 이벤트 루프에 일을 맡길 때 | Session이 `unregisterCh`로 종료를 알림 |
| 콜백 함수 | 호출한 자리에서 바로 허용 여부나 처리 결과가 필요할 때 | Session이 메시지 발행 함수와 처리율 제한 함수를 호출 |

메시지 발행과 처리율 제한 검사는 부모 액터 루프의 직렬 처리가 필요하지 않습니다. Session은 주입된 함수를 호출하고 그 결과에 따라 다음 동작을 결정합니다.

### 3.4 JetStream 수락과 비동기 배치 저장

MongoDB 저장까지 동기로 기다리면 DB 쓰기 지연이 실시간 전달 경로에 포함됩니다. 반대로 Core NATS로 전달만 하면 송신 Pod나 저장 경로의 장애 이후 수락 메시지를 다시 처리할 기반이 없습니다. websocket-service는 JetStream 기록을 수락 경계로 삼아 재처리할 메시지를 남기고, chat-service가 MongoDB 저장을 비동기로 맡습니다.

이 선택은 브로커 기록 비용을 실시간 지연에 포함하는 대신 DB 쓰기 지연을 송신 경로에서 분리합니다. 저장은 배치로 묶어 개별 쓰기 비용을 줄일 수 있지만 이력 반영이 늦어지므로, 클라이언트는 echo 수신과 조회 결과를 합치고 늦게 저장된 메시지를 반복 조회해야 합니다.

#### 저장 대기와 소비

chat-service는 시작할 때 아래 스트림과 공유 durable consumer를 생성·갱신합니다. durable consumer는 처리 진행 상태를 유지하므로 워커가 바뀌어도 미처리 메시지를 이어서 소비할 수 있습니다. 두 스트림 모두 파일 저장소, 복제본 1개, `DiscardNew` 정책을 사용하며 시간 경과에 따른 메시지 만료는 설정하지 않습니다.

| 항목 | 기본 설정 |
| :--- | :--- |
| 저장 스트림 | `CHAT_PERSIST`, subject `chat.persist.*`, WorkQueue retention, 최대 1GiB |
| 중복 수락 억제 | `Nats-Msg-Id`, 중복 확인 기간 2분 |
| 실시간 전달 | `chat.persist.*` → `room.msg.$1` Core RePublish |
| consumer | `chat-persistence`, explicit ACK, `AckWait=30s`, `MaxDeliver=-1`, `MaxAckPending=8000` |
| DLQ | `CHAT_PERSIST_DLQ`, subject `chat.dlq.persistence`, 최대 128MiB |

용량이 차면 `DiscardNew`로 새 수락을 거절해 기존 저장 대기 메시지를 보존합니다. 저장 중단을 흡수할 수 있는 범위는 스트림 용량까지이며, DLQ는 자동 재처리하지 않습니다.

여러 chat-service Pod는 같은 durable pull consumer에서 메시지를 가져와 나눠 처리합니다. 기본 워커 수는 Pod당 1개이며, 최대 500개 또는 100ms 단위로 배치를 가져옵니다. 배치가 커질수록 쓰기 비용을 여러 메시지에 나눌 수 있지만 이력 반영도 늦어지므로, 건수와 대기 시간을 함께 제한합니다.

MongoDB에는 unordered `InsertMany`와 `w:1, j:true`로 저장합니다. `AckWait`은 저장 제한 시간과 배치 대기 시간의 합보다 길게 설정해, 정상적으로 저장하는 중에 불필요하게 재전달되는 일을 줄입니다.

#### 멱등성과 실패 처리

저장 후 ACK가 유실되거나 클라이언트가 재전송하면 같은 논리 메시지를 다시 처리할 수 있습니다. JetStream은 방·발신자·`client_msg_id`·종류·본문 해시를 `Nats-Msg-Id`로 사용해 2분 이내 중복 수락을 억제합니다. 중복 확인 기간이 지난 뒤의 중복은 MongoDB의 유니크 인덱스와 문서 대조로 처리합니다.

중복 키가 있으면 방·발신자·클라이언트 ID·종류·본문을 비교해 같은 내용일 때만 성공으로 봅니다. 같은 키로 다른 내용이 들어오면 영구 충돌로 처리하며, write concern 오류처럼 저장 결과가 불확실하면 재시도합니다. 배치 전체가 아니라 문서별로 결과를 판단합니다.

| 결과 | 처리 |
| :--- | :--- |
| 저장 성공 또는 내용이 같은 중복 | 원본 ACK |
| 일시 오류·결과 불명 | 무작위 재시도 지연을 적용한 NAK, 재전달 |
| 파싱·검증 오류 또는 내용 충돌 | DLQ 발행 성공 후 원본 ACK |
| DLQ 발행 실패 | 원본 ACK 없이 지연 NAK |

일시 오류가 난 메시지는 실패 횟수나 장애가 지속된 시간만으로 DLQ에 보내지 않습니다. 배치 처리가 연속 3회 실패하면 Pod의 회로 차단기가 작동해 모든 워커가 새 메시지를 가져오지 못하게 합니다. MongoDB 상태 점검 실패는 조회 불가 상태로 반영하지만, 정상적으로 소비 중인 워커를 직접 차단하지는 않습니다.

Pod당 하나의 점검 작업이 DB 복구를 확인하면 워커 하나만 시험 배치를 처리합니다. 그 배치가 성공해야 정상 소비를 재개하며, 빈 배치를 받았다는 이유만으로 차단을 해제하지 않습니다.

이 정책은 일시 장애의 메시지를 보존하면서 재시도 부하를 제한합니다. 영구 오류는 DLQ에 남겨 소비를 계속할 수 있게 하지만, 별도의 원인 분석과 처리 판단이 필요합니다. 저장 대기 메시지 보존은 NATS 데이터가 유지된다는 전제에 의존합니다.

### 3.5 저장소 분리와 데이터 정합성

사용자·방·멤버십은 관계와 제약 조건이 중요하므로 PostgreSQL에 저장합니다. 채팅 이력은 MongoDB로 분리해 대량 메시지 저장·조회 부하를 도메인 트랜잭션과 독립적으로 처리합니다. Redis는 TTL과 원자 처리가 필요한 인증·티켓·처리율 제한 상태를 맡습니다.

이 분리는 서비스별 확장을 가능하게 하지만, 도메인 변경과 실시간 알림이 하나의 트랜잭션으로 완료되는 것은 아닙니다. 방 삭제 후 제어 이벤트 실패처럼 저장소 밖의 전달 실패는 별도로 고려해야 합니다.

#### 도메인 트랜잭션과 인덱스

조회 후 변경하는 방 연산은 트랜잭션과 `SELECT FOR UPDATE` 행 잠금으로 경쟁 조건을 제어합니다. 특히 정원 검사와 참여 등록, 방장 위임은 동일한 방 상태를 기준으로 처리해야 합니다. 요청이 경쟁할 때는 잠금 대기를 감수해 도메인 제약을 지킵니다. 실시간 채팅은 이 방 변경 트랜잭션을 거치지 않으므로, 도메인 변경과 메시지 전달은 각각의 정합성 규칙에 따라 처리됩니다.

| 연산 | 보호 대상 | 잠금 방식 |
| :--- | :--- | :--- |
| 채팅방 참여 | 정원 초과 방지 | `rooms` 행 `FOR UPDATE` |
| 채팅방 생성 | 방 생성 + 방장 멤버 추가 원자성 | 트랜잭션 |
| 채팅방 수정 | 정원 축소 시 현재 인원 수 검증, 참여/삭제와의 경쟁 조건 방지 | `rooms` 행 `FOR UPDATE` |
| 채팅방 삭제 | 참여와의 경쟁 조건 방지, 방장 권한 검증 원자성 | `rooms` 행 `FOR UPDATE` |
| 채팅방 나가기 | 방장 위임 경쟁 조건 방지, 빈 방 자동 삭제 | `rooms` 행 `FOR UPDATE` |

인덱스는 실제 조회와 무결성 제약을 기준으로 구성합니다.

| 대상 | 종류 | 용도 |
| :--- | :--- | :--- |
| `users.username` | UNIQUE | 로그인, 중복 방지 |
| `room_members.room_id` | INDEX | 방별 멤버 목록 |
| `rooms.manager_id` | INDEX | 방장별 방 조회 |
| `rooms.name` | GIN (`pg_trgm`) | 방 이름 중간 일치 검색(`ILIKE '%keyword%'`) |

방 이름은 중간 일치 검색(`ILIKE '%keyword%'`)이 필요해 일반 B-tree보다 `pg_trgm` GIN 인덱스가 적합합니다. 도메인 관계는 외래키와 유니크 제약으로 보호합니다.

#### 메시지 저장 제약

| 인덱스 | 종류 | 용도 |
| :--- | :--- | :--- |
| `_id` | UNIQUE | 메시지 ID 중복 방지 |
| `{ roomId, senderId, clientMsgId }` | UNIQUE | 같은 방·발신자의 재전송 중복 방지 |
| `{ roomId, _id }` | INDEX | UUIDv7 기반 이력·복구 조회 |
| `{ createdAt }` | TTL (90일) | 오래된 메시지 자동 파기 |

작성자 이름을 복제하지 않고 ID만 저장해 프로필과 메시지 이력의 결합을 줄입니다. 이름은 조회 시 보충하며, 사용자 삭제가 메시지 조회 자체를 막지 않습니다.

### 3.6 bcrypt 워커 풀

bcrypt는 무차별 대입을 어렵게 만들기 위해 의도적으로 많은 CPU 연산을 수행하는 해시 알고리즘입니다. DB나 네트워크 I/O는 응답을 기다리는 동안 다른 고루틴에 CPU를 양보할 수 있지만, bcrypt는 해싱하는 동안 CPU를 계속 사용합니다. 동시에 Go 코드를 실행할 수 있는 CPU 수는 `GOMAXPROCS`로 제한되므로, 해싱 고루틴을 늘려도 처리량이 그만큼 늘지는 않습니다.

가입·로그인 요청마다 bcrypt를 바로 실행하면 많은 해싱 작업이 한정된 CPU 시간을 나눠 갖습니다. 요청이 처리 속도보다 빠르게 들어올수록 실행 대기와 응답 지연이 누적되고, 같은 user-service의 사용자·방 관리 요청도 CPU 경합의 영향을 받습니다. 따라서 인증 부하를 제어하려면 동시에 실행하는 해싱 수와 대기시키는 작업 수를 함께 제한해야 합니다.

user-service는 bcrypt 작업을 워커 풀에 제출합니다. 풀을 만들 때 `runtime.GOMAXPROCS(0)`를 기준으로 워커 수를 정해 동시에 실행할 해싱 수를 제한합니다. 일시적인 요청 증가는 크기가 제한된 큐로 흡수합니다. 큐가 가득 차면 추가 대기 없이 `ErrQueueFull`을 반환하며, 서비스는 이를 gRPC `ResourceExhausted`로 변환해 과부하를 호출자에게 알립니다.

이 설계는 과부하 시 일부 인증 요청을 거절하는 비용을 감수하고, 실행 중인 해싱 수와 대기열의 크기를 제한합니다. 큐를 크게 잡으면 순간 부하를 더 수용할 수 있지만 대기 시간이 길어지고, 작게 잡으면 거절이 빨라집니다. 워커 풀 자체가 CPU 처리 용량을 늘리지는 않으므로, 지속적인 부하에는 처리 용량과 호출자의 재시도 정책도 함께 고려해야 합니다.

대기 중인 작업 수, 큐 포화로 거절된 작업 수, bcrypt 연산 시간과 처리 결과를 메트릭으로 관측합니다. 처리 가능한 양을 넘는 요청은 계속 쌓아 두지 않고 거절해 호출자에게 과부하를 알립니다(backpressure). 이 지표를 통해 CPU 연산이 느린지, 대기열이 포화된 것인지 구분하고 워커 수와 큐 크기를 판단할 수 있습니다.

### 3.7 애플리케이션 ID 생성과 UUIDv7 정렬

사용자, 채팅방, 메시지 같은 주요 ID는 DB가 아니라 애플리케이션에서 UUIDv7로 생성합니다. ID 생성 시점과 저장 시점을 분리해, 저장 전에 로그와 응답 객체에서 같은 식별자를 사용할 수 있게 하기 위해서입니다.

UUIDv7은 생성 시각을 포함하므로 대략적인 시간순 정렬과 로그 추적에 유리합니다. UUIDv4보다 B-tree 삽입 위치가 덜 분산되어 인덱스 관리에도 부담이 적습니다.

애플리케이션에서 ID를 만들면 INSERT 전에 식별자가 확정됩니다. DB에서 생성한 ID를 받아 오는 과정 없이 관련 데이터의 외래키(FK)를 설정할 수 있고, 비동기 저장 파이프라인에서도 브로드캐스트와 저장을 분리하기 쉽습니다. chat-service는 저장 메시지에 `created_at`이 없으면 UUIDv7의 시각으로 채웁니다.

메시지 정렬과 조회 커서는 UUIDv7 ID를 사용합니다. Pod들이 전역 순번을 협의하는 단계를 송신 경로에 두지 않는 대신, 생성 시각과 전달 순서의 차이를 허용합니다. 클라이언트는 ID로 정렬하고 복구 커서를 되감아 늦게 저장된 메시지를 찾습니다. UUIDv7은 연속 순번이나 인과 순서가 아니므로, 번호가 비어 있는지 확인하는 방식으로 모든 누락을 검출할 수는 없습니다.

## 4. Kubernetes 배포와 운영 경계

배포 환경은 고정된 Pod 수에서 부하와 정합성을 확인하고, Pod 수가 바뀌는 상황에서 연결·복구 동작을 확인할 수 있도록 구분합니다. 로컬 kind의 컨트롤 플레인 노드 1개와 워커 노드 1개를 사용하며, Calico가 Pod 네트워크와 NetworkPolicy를 적용하고 공용 Traefik이 환경별 Gateway와 HTTPRoute를 처리합니다.

### 4.1 리소스와 환경 구분

| 리소스 | 역할 |
| :--- | :--- |
| Deployment | 앱, PostgreSQL·MongoDB·Redis, 관측성 서비스 |
| StatefulSet | 단일 NATS 인스턴스와 고정 Pod 이름; 현재 볼륨은 `emptyDir` |
| ClusterIP Service | HTTP/WebSocket과 데이터 서비스의 내부 진입점 |
| Headless Service | user/chat gRPC 대상 발견, NATS의 고정 DNS |
| GatewayClass / Gateway / HTTPRoute | Traefik 선택, 환경별 호스트와 외부 경로 연결 |
| Job | 스키마 마이그레이션과 k6 부하 실행 |

공통 매니페스트는 `deploy/k8s/base`에, 환경별 차이는 `deploy/k8s/overlays`에 둡니다. CPU·메모리 요청량과 메모리 상한, 보안 설정은 공통 설정에서 정의합니다. Go 서비스는 일반 사용자 권한과 읽기 전용 루트 파일 시스템으로 실행하며, 리눅스 capability를 제거하고 ServiceAccount 토큰의 자동 마운트를 비활성화합니다.

| 환경 | 목적 | 구성 |
| :--- | :--- | :--- |
| `dev` | 로컬 개발과 C10K 부하 확인 | WebSocket Pod 2개, 나머지 앱은 기본 1개 |
| `test` | 반복 가능한 E2E | 핵심 Go 서비스 Pod 2개, MongoDB 연결 장애 주입용 Toxiproxy |
| `qa` | 확장·축소 중 전달과 복구 검증 | WebSocket 활성 연결 수 기반 HPA, Pod 1~2개 |

`dev`와 `qa`는 주요 Go 서비스의 TCP accept queue를 조정합니다. user-service의 CPU 상한은 공통 설정에서 4코어로 지정하며, bcrypt의 병렬 처리 범위를 제한합니다.

### 4.2 설정 주입과 배포 순서

앱 이미지는 환경과 무관하게 빌드하고 실행 차이는 Kustomize 오버레이로 주입합니다. ConfigMap의 `base.yaml`과 환경별 `override.yaml`을 읽은 뒤 `APP_` 환경변수를 병합하고 검증합니다. 필수 값이 비거나 범위를 벗어나면 시작하지 않습니다.

| 설정 | 주입 방식 |
| :--- | :--- |
| 포트·타임아웃·서비스 주소 | ConfigMap 기본 설정 |
| 환경 이름·관측성 주소·테스트 제한값 | 오버레이의 설정 파일 |
| 인증 시크릿·DB 접속 정보 | Secret의 환경변수 |
| Pod 식별자 | Downward API의 `POD_NAME` |

`test`는 HTTP 요청과 WebSocket 연결 제한을 완화하되 채팅 전송 제한은 기본값을 유지합니다. 앱 설정 구조체와 환경변수 접두사를 통해 Kubernetes의 자동 Service 환경변수와 구분합니다.

`make dev-up`, `make test-up`, `make qa-up`은 kind와 플랫폼을 준비하고 이미지를 빌드·적재한 뒤 [bootstrap.sh](../deploy/k8s/scripts/bootstrap.sh)를 실행합니다. 플랫폼 준비 단계에서 Calico, Gateway API CRD, Traefik을 설치합니다.

| 단계 | 적용 대상 | 완료 조건 |
| :--- | :--- | :--- |
| `foundation` | Secret, 데이터 계층, Gateway, NetworkPolicy | DB Deployment와 NATS StatefulSet 준비 |
| `observability` | 관측성 스택, QA의 Prometheus Adapter | Deployment 롤아웃 완료 |
| `migrations` | PostgreSQL·MongoDB migration Job | 두 Job 성공 |
| `apps` | 앱 설정, OpenAPI, Deployment, HTTPRoute | 앱 롤아웃 완료와 Gateway `Programmed` |

마이그레이션이 실패하면 앱 배포를 진행하지 않습니다. 앱 이미지는 Git 리비전과 작업 트리 내용으로 만든 태그를 사용하고 kind에 적재한 이미지만 실행합니다. 설정·명세는 Kustomize의 해시가 붙은 ConfigMap으로 생성하므로 이미지나 설정 변경이 Pod 템플릿에 반영되어 롤아웃을 유발합니다.

스키마와 인덱스는 타임스탬프 버전의 마이그레이션 파일에서 관리하며 `golang-migrate`로 적용합니다. 앱 시작 시 인덱스를 자동 생성하지 않아 스키마 변경의 실행 경계를 명확히 합니다.

### 4.3 외부 경로와 보안 경계

Traefik은 `gochat-system` 네임스페이스에 두고, 각 환경의 Gateway는 같은 네임스페이스의 HTTPRoute만 받습니다. 로컬 진입점은 `http://{dev|test|qa}.gochat.localhost:30080`이며 호스트 포트는 `127.0.0.1`에만 바인딩합니다.

| 경로 | 대상 | 처리 |
| :--- | :--- | :--- |
| `/` | `frontend` | 정적 파일 |
| `/api` | `api-gateway` | `/api` 접두사 제거 후 REST 전달 |
| `/ws` | `websocket-service` | WebSocket 연결 전환 |
| `/docs` | `swagger-ui` | OpenAPI 문서 |
| `/grafana` | `grafana` | 관측 대시보드 |

프론트엔드와 API를 같은 호스트에 두어 동일 출처에서 인증 쿠키를 사용합니다. Traefik은 컨트롤 플레인의 호스트 포트로 요청을 받고, 긴 WebSocket 연결을 위해 entrypoint의 read/idle timeout을 조정합니다.

NetworkPolicy는 환경 네임스페이스 사이의 트래픽을 격리하고, 같은 네임스페이스 내부 통신과 DNS를 허용합니다. Traefik의 공개 서비스 접근, 관측성 컴포넌트의 Kubernetes API 접근, custom metrics 조회는 예외로 열어 둡니다. 이는 환경 격리이며 서비스별 최소 권한 통신이나 NATS 인증·TLS를 대신하지 않습니다.

WebSocket 내부 HTTP는 공유 Secret으로 보호하며, 외부 HTTPRoute는 `/ws`만 websocket-service에 연결합니다. 프론트엔드 컨테이너의 Nginx는 정적 파일만 제공합니다. 로컬 프론트엔드 개발에서는 Vite가 API를 프록시합니다.

`local-secret.yaml`은 로컬 샘플 값만 담습니다. 실제 인증 정보는 외부 Secret 저장소나 배포 파이프라인에서 주입해야 합니다. HTTPS, NATS 인증·TLS와 서비스별 최소 권한 네트워크 정책은 이 로컬 배포에 포함되지 않습니다.

### 4.4 서비스 발견과 HPA

api-gateway와 websocket-service는 ClusterIP Service를 외부 라우팅 대상으로 사용합니다. user-service와 chat-service는 Headless Service를 사용하며, gRPC 클라이언트는 `ClientConn`을 재사용하고 Pod 주소를 대상으로 `round_robin` 방식으로 요청을 분산합니다.

기존 연결이 정상일 때는 새 Pod를 찾기 위한 DNS 재조회가 보장되지 않습니다. 따라서 Pod 수가 바뀌어도 조회 RPC가 곧바로 새 Pod에 분산된다고 볼 수는 없습니다. chat-service 저장 워커는 gRPC 분산과 별개로 동일 durable consumer에 참여합니다.

QA HPA는 Prometheus Adapter의 Pod별 활성 연결 수를 사용합니다. 대상은 websocket-service이며 목표는 Pod당 연결 100개, Pod 수는 1~2개로 조절합니다. 열린 연결은 증설한 Pod로 이동하지 않으며 축소로 끊어진 연결은 재접속합니다.

### 4.5 Probe와 프로세스 종료

| Probe | 기준 |
| :--- | :--- |
| startup | 앱 초기화 대기 |
| liveness | HTTP `/health`, gRPC TCP 연결로 프로세스 생존 확인 |
| readiness | HTTP `/ready`, 기본 gRPC 상태 검사로 트래픽 수신 가능 상태 확인 |

의존성 장애를 프로세스 장애로 간주해 재시작하지 않도록 liveness와 readiness를 구분합니다. 서비스별 readiness는 [메시지 수락과 조회의 장애 경계](#32-메시지-수락과-조회의-장애-경계-분리)를 따릅니다.

HTTP/gRPC 서버는 새 요청을 막고 진행 중인 요청의 종료를 기다립니다. HTTP 서버의 종료 절차는 WebSocket 연결이 닫힐 때까지 기다리지 않으므로 Manager가 Hub·세션을 닫고 구독을 해제합니다. chat-service는 새 메시지 수신을 멈추고 이미 가져온 배치를 저장 제한 시간 안에 처리합니다. ACK하지 않은 메시지는 NATS 데이터가 유지되는 동안 다시 전달됩니다.

### 4.6 데이터 수명과 보존 한계

로컬 검증 환경은 필요할 때 다시 생성할 수 있지만, 데이터는 저장소 Pod가 유지되는 동안만 보존됩니다.

| 저장소 | 배포 | 로컬 저장 방식 |
| :--- | :--- | :--- |
| PostgreSQL | Deployment + ClusterIP | `emptyDir` |
| MongoDB | Deployment (`Recreate`) + ClusterIP | `emptyDir` |
| Redis | Deployment + ClusterIP | `emptyDir`, 영속 볼륨 없음 |
| NATS JetStream | StatefulSet (Pod 1개) + Headless Service | `emptyDir`의 파일 저장소 |

같은 Pod 안의 컨테이너 재시작과 Pod 교체는 다릅니다. `emptyDir`은 전자에는 남지만 Pod 삭제·교체 시 사라집니다. 따라서 MongoDB 이력과 JetStream 저장 대기 메시지의 Pod 교체 후 보존을 보장하지 않으며, 복제·백업은 제공하지 않습니다. 관측성 데이터 역시 로컬 임시 볼륨에 둡니다.

## 5. 관측성 설계

전달 지연이 낮다는 사실만으로 처리 효율이 좋아졌다고 볼 수는 없습니다. 더 많은 요청을 거절하거나 메시지를 버린 결과일 수 있고, 대기가 저장 경로에 쌓이고 있을 수도 있습니다. 관측성은 이 차이를 구분하기 위해 구성합니다. 전달 지연을 처리량·오류·대기량과 함께 보고, 트레이스와 로그로 요청 맥락을 확인하며, 프로파일로 CPU 병목의 원인을 좁힙니다.

앱의 OpenTelemetry SDK는 메트릭과 트레이스를 OTLP/HTTP로 Alloy에 전송합니다. Alloy는 NATS exporter, kube-state-metrics, cAdvisor의 지표도 수집합니다. 로그는 앱이 `slog`로 표준 출력에 기록하고, Alloy의 `loki.source.kubernetes`가 Kubernetes API를 통해 읽습니다.

Alloy는 수집한 로그를 Loki Push API로, 메트릭을 Prometheus Remote Write로, 트레이스를 Tempo OTLP/HTTP로 전달합니다. 프로파일은 앱의 `pyroscope-go`가 Pyroscope로 직접 보냅니다.

### 5.1 신호 구성

| 신호 | 백엔드 | 용도 |
| :--- | :--- | :--- |
| 로그 | Loki | 이벤트 기록 검색 |
| 메트릭 | Prometheus | 이상 감지 |
| 트레이스 | Tempo | 서비스 간 요청 흐름 추적 |
| 프로파일 | Pyroscope | 코드 수준의 병목 분석 |

### 5.2 계측 기준

| 기준 | 적용 |
| :--- | :--- |
| 상관관계 | HTTP/gRPC 요청 경계에서 트레이스 컨텍스트 전파 |
| 노이즈 제거 | `/health`, `/ready`, 메트릭 엔드포인트는 로그/트레이스 수집에서 제외 |
| 민감정보 보호 | 토큰/비밀번호/시크릿 쿼리 파라미터 마스킹, DB 쿼리문 노출 통제 |
| 카디널리티 제어 | URL 경로의 UUID를 `:id`로 정규화 |
| 계측 범위 | HTTP/gRPC, 저장소, WebSocket/NATS, JetStream 저장 처리, 인증 경로 계측 |
| 샘플링 | 트레이스는 10% 샘플링 |

Probe 제외와 경로 정규화는 분석 노이즈와 시계열 증가를 억제합니다. 트레이스 샘플링은 수집 비용을 제한하며, 개별 요청의 기록이 항상 남는 것은 아닙니다.

### 5.3 통합 조회

Grafana에서는 전체 상태를 먼저 살펴보고, API 트래픽·실시간 메시징·저장소·실행 환경 지표 순으로 장애 범위를 좁힙니다.

| 대시보드 | 내용 |
| :--- | :--- |
| Operations Overview | 발생 중인 경보, 가용성, 지연, 트래픽, 실시간 전달·저장·실행 환경의 핵심 상태 |
| API Traffic | HTTP/gRPC 요청률·지연·오류, 경로·메서드별 주요 지표 |
| Realtime Messaging | WebSocket 연결, 초당 메시지 수, 폐기·처리율 제한, NATS, UUID 순서 역전, 메시지 분배 |
| Data Persistence | PostgreSQL·MongoDB·Redis 연결 풀과 저장 지표 |
| Platform Runtime | Kubernetes Pod 수·재시작·HPA, 컨테이너 CPU·메모리, Go 런타임 |

NATS 메시지 경계에서는 트레이스 컨텍스트를 전파하지 않습니다. 메시지 전달과 저장 경로는 전용 메트릭과 프로파일로 확인합니다. 저장 대기량·지연·재시도·DLQ와 Pod별 회로 차단 상태는 [텔레메트리 카탈로그](TELEMETRY_CATALOG.md#persistence)에 정리합니다.

`trace_id`를 기준으로 Loki 로그와 Tempo 트레이스를 연결합니다. 로그·트레이스·프로파일은 Grafana Explore와 상세 탐색 화면에서 확인합니다. 같은 요청의 정보를 연결해 분석 중 불필요한 화면 전환을 줄입니다.

### 5.4 저지연과 정합성을 함께 판단하는 지표

| 판단 대상 | 함께 보는 신호 |
| :--- | :--- |
| 부하 중 전달 지연이 유지되는가 | 전달 지연과 초당 메시지 수, 활성 연결 수, CPU·메모리 |
| 낮은 지연이 거절·누락을 가리고 있지 않은가 | 발행 실패, 전송 프레임 폐기, 처리율 제한, NATS의 느린 소비자 |
| 지연이 저장 경로로 밀리고 있지 않은가 | JetStream 저장 대기 메시지, 저장 지연, 재시도, 회로 차단 상태, DLQ |
| 인증 부하를 감당할 수 있는가 | bcrypt 연산 시간, 큐 대기 작업 수, 큐 포화 거절 수 |

메트릭은 병목과 이상 징후를 찾는 수단이며, 개별 메시지 정합성의 증거는 아닙니다. 낮은 전달 지연과 오류율만으로 성공을 판단하지 않고, 검증 시 메시지 ID·내용과 최종 저장 결과를 대조합니다.

## 6. 테스트 전략과 검증 범위

검증은 저지연과 정합성을 함께 평가합니다. 메시지를 버리거나 저장 대기를 계속 늘리면서 전달 지연만 낮추는 것으로는 두 목표를 충족할 수 없습니다. 스케일아웃으로 연결을 더 수용하는지와 그 과정에서 메시지가 올바르게 전달·저장되는지를 별도로 확인합니다.

| 목표 | 확인할 결과 | 함께 확인할 비용 |
| :--- | :--- | :--- |
| 부하 중 저지연 | 송신부터 echo까지의 지연 분포와 처리량 | 송신 오류·타임아웃·메시지 폐기, CPU·메모리, 저장 대기량 |
| 확장 중 정합성 | 확인한 메시지 집합과 DB 집합의 일치, 논리 중복·내용 충돌 처리 | 재연결, 실시간 중복 전달, 이력 반영·복구 지연 |
| 장애 후 복구 | 재전달과 저장 재개 후 메시지 반영 | 저장 대기 메시지 처리 완료, 재시도·DLQ, 복구에 걸리는 시간 |

### 6.1 테스트 계층

빠른 로직 검증과 실제 의존성의 동작 검증을 분리합니다. 각 계층은 서로 다른 실패 원인을 드러냅니다.

| 계층 | 빌드 태그 | 실행 환경 | 주요 검증 대상 |
| :--- | :--- | :--- | :--- |
| 단위 | 없음 | mock·stub·fake·miniredis | 도메인 규칙, 오류 분기, 상태 전이 |
| 통합 | `integration` | Testcontainers의 PostgreSQL·MongoDB·Redis·NATS | 트랜잭션, 원자 처리, 중복·부분 실패, JetStream 수락·재전달 |
| E2E | `e2e` | 준비된 kind `test` 환경 | 실제 REST/WebSocket 사용자 흐름, 다중 Pod, 저장 장애 복구 |

단위 테스트는 외부 프로세스에 의존하지 않고 병렬 실행을 기본으로 합니다. 실제 서버 설정·프로토콜에 의존하는 동작은 통합 테스트가 맡습니다. 통합·E2E는 데이터를 초기화하고 시나리오를 순차 실행해 상태 간섭을 줄입니다.

### 6.2 장애 복구와 정합성 검증

E2E는 대상 네임스페이스의 서비스가 준비되었는지 확인한 뒤 사용자 흐름을 실행합니다. MongoDB 장애는 Toxiproxy로 연결만 차단하고, MongoDB Pod와 프로세스는 유지합니다. 이 상태에서 chat-service 재시작·Pod 수 변경과 연결 복구 후 저장 재개를 확인합니다.

장애 테스트는 echo로 확인한 메시지 ID 집합과 최종 DB 집합을 비교하고 누락·중복, 저장 대기량과 DLQ를 함께 확인합니다. 연결 성공이나 오류율 0만으로 전달·저장 정합성을 판단하지 않습니다.

| 대상 | 검증 관점 |
| :--- | :--- |
| WebSocket 분산 | 여러 Pod의 같은 방 참여자에게 전달 |
| 저장 워커 | ACK하지 않은 작업의 재전달, 재시작·Pod 수 변경 후 저장 |
| MongoDB 연결 장애 | JetStream 저장 대기 메시지 유지, 연결 복구 후 DB 반영 |
| WebSocket HPA | 확장 시 기존 연결 유지, 축소 시 재연결과 이력 복구 |
| 프론트엔드 | UUIDv7 정렬, 메시지 키별 중복 제거, 제한된 기간의 복구 |

### 6.3 실행 경로와 측정 범위

단위 테스트는 `go test ./...`, 통합 테스트는 `go test -count=1 -tags=integration ./...`로 실행합니다. E2E는 다음과 같이 환경을 먼저 준비합니다.

```bash
make test-up
go test -count=1 -tags=e2e ./test/e2e
```

E2E 실행기는 클러스터 밖에서 Traefik을 거쳐 HTTP/WebSocket에 접근합니다. k6 부하는 클러스터 내부 Service에 직접 요청하므로 Traefik 구간의 지연·처리량은 측정하지 않습니다.

| 명령 | 환경 | 목적 |
| :--- | :--- | :--- |
| `make dev-load` | `dev`, k6 Pod 4개 | C10K 연결과 메시지 수락·전달 부하 |
| `make qa-load` | `qa`, k6 Job 1개 | WebSocket HPA 확장과 재연결·복구 |

`qa-load`는 WebSocket Pod 수를 1개로 되돌린 뒤 HPA를 붙입니다. 부하 실행은 환경 준비와 분리되어 있습니다.

### 6.4 검증 결과의 적용 범위

지연은 측정 구간·부하 조건·표본과 함께 해석합니다. 송신부터 echo까지의 지연은 MongoDB 저장 완료 시간이나 모든 수신자의 지연을 나타내지 않습니다. 또한 워커별 P99를 전체 요청의 통합 P99로 간주하지 않습니다.

측정값과 실행 조건은 [C10K 보고서](K8S_JETSTREAM_C10K_REPORT.md)와 [HPA·장애 복구 보고서](K8S_JETSTREAM_HPA_REPORT.md)에서 확인할 수 있습니다. 결과는 명시된 실행 구성과 메시지 집합에 한정되며, 현재 배포의 성능이나 데이터 보존을 포괄적으로 보장하지 않습니다.

저장소 Pod 교체·디스크 영구 손실에 대한 무손실, 장시간 장애, 임의의 시계 차이, 모든 실시간 프레임의 누락 검출은 보장 범위에 포함하지 않습니다. 애플리케이션의 재시도·멱등성 검증과 저장 인프라의 데이터 보존은 별도 경계입니다.
