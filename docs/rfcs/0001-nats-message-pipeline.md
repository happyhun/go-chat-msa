# RFC-0001: NATS 기반 메시지 전달·저장·복구 통합

| 항목 | 내용 |
| :--- | :--- |
| 상태 | Accepted |
| 작성자 | happyhun |
| 결정 기준일 | 2026-09-24 |
| 비교 범위 | `main` → `dev` |
| 대상 | WebSocket 라우팅, 메시지 수락·저장, 재연결·이력 복구 |
| 기준 문서 | [설계](../DESIGN.md), [기존 C10K](../K8S_C10K_REPORT.md), [NATS C10K](../K8S_NATS_C10K_REPORT.md) |

## 0. 요약

ws-gateway와 방 소유권을 제거하고, Kubernetes Service가 WebSocket 연결을 분산한다. 각 Pod는 로컬 세션만 관리하며 NATS로 같은 방의 메시지를 교환한다. JetStream 기록을 수락 경계로 삼고 MongoDB 저장은 별도 워커가 수행한다.

소유권 이전과 프로세스 로컬 저장 큐를 없애는 대신 브로커 의존성과 비동기 이력 반영을 감수한다. 전달 연속성을 잃은 연결은 종료하고 재연결·이력 동기화로 복구한다. C10K 메시지 P99 레이턴시 19ms와 HPA 확장·강제 축소 중 메시지 정합성을 확인해 채택한다.

## 1. 배경과 목표

| `main`의 구조 | 변경 이유 |
| :--- | :--- |
| ws-gateway가 모든 WebSocket 프레임 중계 | 중계 비용과 운영 구성 요소 제거 |
| consistent hashing·멤버십·방 lease·소유권 이전 | 확장·축소를 방 이동 절차와 분리 |
| 방 담당 Pod가 연속 순번 발급 | 같은 방을 여러 Pod에서 처리하면서 연속 순번을 유지하려면 중앙 발급·조정이 필요하므로 UUIDv7로 전환 |
| WebSocket 프로세스의 메모리 큐에서 배치 저장 | 프로세스 종료로 미처리 저장 작업이 사라지는 구간 제거 |

목표는 C10K 메시지 P99 50ms 미만을 유지하면서 확장·재연결·저장 장애 시 복구 경로를 단순화하는 것이다. 로컬 단일 호스트·단일 worker 노드 조건은 유지한다.

## 2. 제안

### 2.1 전달과 저장

1. api-gateway가 일회성 티켓을 발급하고, websocket-service가 티켓·멤버십과 방 구독 준비를 확인한 뒤 연결을 수락한다.
2. websocket-service가 채팅을 검증하고 UUIDv7 ID를 생성해 `chat.persist.{roomID}`에 발행한다. 성공 `PubAck`가 서버의 수락 기준이다.
3. JetStream 기록 후 `room.msg.{roomID}`로 RePublish하고, 구독 Pod들이 로컬 세션에 전달한다.
4. chat-service의 워커들이 하나의 durable pull consumer를 공유한다. 최대 500건 또는 100ms 단위로 MongoDB에 저장하고, 성공 또는 내용이 같은 중복에만 ACK한다.

JetStream은 `WorkQueue`·`DiscardNew`로 미처리 작업을 보호하고 용량이 차면 신규 수락을 거부한다. 일시 오류는 지연 재전달하고, DB 장애가 지속되면 회로 차단기로 pull을 중단한다. 영구 오류는 DLQ 기록에 성공한 뒤 원본을 ACK한다.

중복 수락은 `Nats-Msg-Id`로 억제하고, 기간 밖의 재전달은 MongoDB 유니크 인덱스와 내용 대조로 처리한다. 발행 timeout은 수락 여부가 모호하므로 같은 `client_msg_id`와 본문으로 조회·재시도한다.

### 2.2 연결 종료와 복구

| 상황 | 정책과 이유 |
| :--- | :--- |
| 세션 전송 큐 포화 | 해당 소켓을 즉시 닫아 누락된 연결을 정상 상태로 유지하지 않음; 다른 세션 전달은 계속 |
| NATS slow consumer | Pod의 NATS 연결을 한 번만 재설정하고 모든 로컬 세션 종료; 손실된 구독의 복구를 재연결 경로로 통일 |
| NATS 재연결 | 기존 Hub·세션 정리가 끝난 뒤 신규 연결 허용; 이전 상태와 새 구독의 혼재 방지 |
| HPA 확장·축소 | 기존 연결은 확장 시 유지, 새 연결부터 분산; 축소로 끊긴 연결은 재접속·이력 동기화 |

`frame_no`와 gap 감지를 제거하고 불변 payload를 공유한다. 클라이언트는 UUIDv7로 정렬하고 서버 ID·논리 메시지 키로 중복을 제거한다. 재연결 시 2초 되감은 복구 시작점을 고정해 최대 60초간 반복 조회하며, 30초 주기로 최근 이력을 보충한다. 빈 응답만으로 복구 완료를 판단하지 않는다.

## 3. 계약 변경

| 계약 | `main` → `dev` |
| :--- | :--- |
| 연결 경로 | ws-gateway의 방별 라우팅 → websocket-service 직접 연결 |
| 티켓 | ws-gateway 발급·소비 → api-gateway 발급, websocket-service 소비 |
| 메시지 정렬·조회 | 연속 순번·`last_seq` → UUIDv7·`after_id`·`has_more` |
| 저장 요청 | WebSocket 로컬 큐·배치 gRPC → JetStream 공유 consumer |
| 수락·echo | 성공 `PubAck`는 브로커 기록 확인; RePublish echo는 MongoDB 저장 완료와 구분 |
| 전달 실패 | 연결 종료 후 저장 이력 조회; 모든 실시간 프레임의 수신 확인이나 replay는 제공하지 않음 |

순번 기반 클라이언트·조회 계약과 호환되지 않는다. 서버·프론트엔드·DB 인덱스를 함께 전환하며, 기존 데이터의 무중단 마이그레이션은 이번 검증 범위에 포함하지 않는다.

## 4. 구현 범위

| 구성 요소 | 변경 |
| :--- | :--- |
| ws-gateway·Redis 제어 상태 | 서비스, 해시 링, 멤버십, 방 lease·순번 기준 제거 |
| websocket-service | NATS 방 구독·발행, 큐 포화 종료, 연결 재설정과 readiness 복구 순서 |
| chat-service | 배치 저장 consumer, 멱등성·재전달·회로 차단·DLQ |
| frontend·API | UUID 커서, 중복 제거·정렬, 고정 시작점 기반 이력 복구 |
| 배포·관측·테스트 | NATS와 연결 수 HPA, 저장·전달 지표, C10K·HPA·장애 복구 검증 |

## 5. 트레이드오프와 한계

같은 방의 메시지를 여러 Pod에서 처리하면서 연속 순번을 유지하려면 중앙에서 순번을 발급·조정해야 한다. 메시지마다 이 경로를 거치지 않도록 UUIDv7을 선택했고, 그 대가로 순번의 빈 구간을 통한 누락 감지를 포기했다. 여러 Pod에서 발행한 메시지는 UUIDv7 순서와 다르게 도착할 수 있어 클라이언트가 ID 기준으로 다시 정렬한다. 이 정렬이 실제 발행 순서를 보장하거나 빠진 메시지가 없음을 확인해 주지는 않는다.

| 변경 | 얻는 것 | 잃는 것·감수하는 비용 |
| :--- | :--- | :--- |
| 방 소유권·ws-gateway 제거 | 소유권 이전 없이 연결 분산, 중계 비용 제거 | NATS가 공통 의존성과 장애점이 됨; 확장해도 기존 연결은 재분배되지 않음 |
| 연속 순번 → UUIDv7 | 중앙 순번 발급 없이 각 Pod에서 메시지 생성 | 순번 기반 누락 감지 포기; 되감기·반복 조회만으로 복구 완전성을 판정할 수 없음 |
| 로컬 저장 큐 → JetStream | WebSocket·저장 워커 종료 후에도 미처리 작업 재전달 | 브로커 기록 비용·용량 관리 추가; 수락과 MongoDB 반영은 여전히 비동기 |
| Core RePublish로 실시간 전달 | Pod별 소비자·ACK 상태 없이 로컬 세션에 fan-out | Pod별 수신 확인·replay 없음; 놓친 채팅은 DB 반영 후 이력 조회에 의존 |
| 큐 포화·slow consumer 시 연결 종료 | 손실이 감지된 연결을 정리하고 재연결·sync로 복구 경로 통일 | 재접속·티켓·조회 부하 증가; NATS slow consumer는 해당 Pod의 모든 세션에 영향 |

현재 보장 범위는 다음으로 제한된다.

- **저장 보존:** NATS는 단일 Pod·복제본 1개, 저장소는 `emptyDir`이다. 재처리는 NATS 데이터가 남아 있는 동안만 가능하며 저장소 Pod 교체·디스크 손실·호스트 장애의 무손실을 보장하지 않는다.
- **이력 복구:** 2초 되감기·60초 반복 조회 범위를 넘는 저장 지연과 시계 차이는 자동 복구 보장 밖이다. 감지되지 않은 누락이나 탭 종료로 잃은 복구 시작점도 완전하게 회수한다고 보장할 수 없다. 비영속 시스템 이벤트는 메시지 이력으로 재생되지 않는다.
- **수락·중복:** echo는 MongoDB 저장 완료가 아니다. 발행 timeout에는 수락 여부가 모호할 수 있으며, DB 멱등성은 실시간 중복 전달까지 막아주지 않는다.
- **처리율 제한:** 사용자·방 메시지 제한은 Pod별이다. 여러 Pod에 세션이 분산되면 클러스터 전체에서 같은 한도를 보장하지 않는다.

## 6. 검증

### 6.1 C10K

2026-09-24 로컬 kind `dev`에서 10,000 VU·100개 방·2K Ingress·200K Egress로 측정했다. k6 워커 4개 모두 기준을 통과했다.

| 지표 | 기존 Kubernetes | 현재 NATS 구성 |
| :--- | :--- | :--- |
| 워커별 메시지 P99 | 41~43ms | 19 / 16 / 12 / 12ms |
| 서버 Fanout 최대 P99 | 6.51ms | 1.53ms |
| 서버 Egress 최대 P99 | 24.2ms | 8.86ms |
| 메시지 타임아웃 | 0 | 0 |

현재 실행의 송신 오류·Pod 재시작과 종료 후 저장 대기·DLQ는 모두 0이다. k6는 Probe의 echo 지연을 측정하며 MongoDB 저장 완료나 전체 메시지 무손실을 뜻하지 않는다. 서버 값은 Pod별 전체 실행 P99 중 최댓값이다. 두 보고서는 런타임·발생기·자원 설정이 달라 NATS만의 개선 효과를 분리한 실험은 아니다. 세부 조건은 [기존 보고서](../K8S_C10K_REPORT.md)와 [최신 보고서](../K8S_NATS_C10K_REPORT.md)에 둔다.

### 6.2 확장·장애 복구

| 검증 | 결과 |
| :--- | :--- |
| kind `qa` HPA 1→2 확장·별도 강제 2→1 축소 | 송수신과 재연결 후 이력 동기화 정상, 최종 누락·중복 없이 모든 k6 기준 통과 |
| MongoDB 연결 장애·저장 워커 재시작·Pod 수 변경 | echo 확인 집합과 최종 DB 집합 대조, 누락·중복과 저장 대기·DLQ 검증 통과 |
| 세션 큐 포화·NATS slow consumer | 단위·통합 테스트에서 종료 범위, 중복 재설정 방지, 정리 후 연결 수용 검증 통과 |
| NATS 재시작 | E2E에서 기존 연결 종료·재접속·이력 복구·실시간 수신 재개 검증 통과 |

큐 포화와 slow consumer의 결정적 재현은 단위·통합 테스트 범위다. HPA·E2E 결과를 브라우저의 모든 자동 복구 동작이나 저장소 영구 손실 검증으로 확대하지 않는다.

## 7. 결론

`dev`의 NATS 전달·저장·복구 구조를 채택한다. 방 소유권과 중계 계층을 제거하면서 C10K 지연 기준과 확장·장애 복구 검증을 충족했다. 상세 동작은 [설계 문서](../DESIGN.md), 관측 지표는 [텔레메트리 카탈로그](../TELEMETRY_CATALOG.md)를 기준으로 한다.
